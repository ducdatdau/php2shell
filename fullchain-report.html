00 — The chain

Five requests, one worker

The exploit is four chain requests — A1 → B1 → A2 → B2 — preceded by a pinning step that forces all four onto the same Apache child. One worker is the whole point: the bug is that request-owned state (a module global, freed heap) survives from one request into the next on the same process, so every stage below shares that worker's heap and session globals.

What hsv is, and why destroying it runs a command

hsv is the PoC's name for PS(http_session_vars) (php_session.h:188) — the session module's own zval that holds $_SESSION. When a session initialises, PHP wraps the $_SESSION array in a reference, parks it here, and registers it in the symbol table as the $_SESSION superglobal:

ZVAL_NEW_REF(&PS(http_session_vars), &session_vars);   # reference → the $_SESSION array
Z_ADDREF_P(&PS(http_session_vars));
zend_hash_update_ind(&EG(symbol_table), "_SESSION", &PS(http_session_vars));   # session.c:248–250

Every $_SESSION access the module makes goes through it — Z_REFVAL(PS(http_session_vars)) in php_set_session_var, php_check_cancel_upload, the write-back encoder. It exists so the module can reach $_SESSION for the life of the request. Nothing exotic — it is ordinary session plumbing.

What makes it the target is how PHP tears it down. At the end of every request, session RSHUTDOWN destroys that reference:

php_rshutdown_session_globals():
    if (!Z_ISUNDEF(PS(http_session_vars))) {
        zval_ptr_dtor(&PS(http_session_vars));   # session.c:140  ← the operation B2 hijacks
        ZVAL_UNDEF(&PS(http_session_vars));
    }

Normally that drops the reference, the $_SESSION array's refcount reaches 0, and zend_array_destroy frees it cleanly. The exploit makes hsv instead point at a fake reference → the fake zend_array at S whose pDestructor = zif_system. So the routine "free $_SESSION" at shutdown becomes "call zif_system":

zval_ptr_dtor(hsv) → drop reference → array refcount 0
  → zend_array_destroy(S) → for its 1 bucket: pDestructor(&arData[0])
  → zif_system( S+0x20 )        # mk_ht lays a fake zend_execute_data at arData = S+0x20
  → reads num_args=1, arg1 = S+0x80 = "id>/out/p1"
  → system("id>/out/p1")

So A2 frees/strands the memory hsv's reference points at, and B2's spray reclaims that freed slot with the fake reference and plants the fake array at S. When the pinned worker reaches RSHUTDOWN, the normal $_SESSION cleanup fires the attacker's destructor instead. It is the same 109618→109619 pattern as A1→B1, one layer up: a controlled OOM frees an object the module will still destroy, and the reclaim decides what that destruction does. The gdb trace's popen("id>/out/p1") happens exactly here, at shutdown.

05 — Inside ZendMM

The memory model the whole chain stands on

Request data never touches malloc directly — it goes through the Zend Memory Manager (ZendMM, Zend/zend_alloc.c), an arena over mmap. Three facts decide everything that follows.

  • Chunks & pages. Memory is carved from 2 MiB chunks, each mmap'd 2 MiB-aligned (zend_alloc_sizes.h:22), split into 512 × 4 KiB pages; page 0 is the chunk header.
  • Three size regimes. small ≤ 3072 B → one of 30 fixed bins (8, 16, 24, … 3072; zend_alloc_sizes.h:32); large 3073 B … ~2 MiB → a run of whole pages; huge > 2 MiB → its own mmap.
  • Alignment is addressing. Because chunks are 2 MiB-aligned, ptr & ~0x1FFFFF is its chunk base — exactly how decode_cookie turns leaked 8-byte values into base addresses (§03).

06 — Mechanism

Why this layout produces a use-after-free

Two allocator disciplines — both confirmed in the 8.4.26 source — make a freed object's successor predictable. That predictability is the whole basis of grooming.

small bins

LIFO free-list → MRU reuse

free_small pushes the freed slot to free_slot[bin]'s head; alloc_small pops the head (zend_alloc.c:1417 / 1395). The next allocation of that size lands on the slot you just freed. Free the victim, allocate your fake → same address.

large runs

Best-Fit over the page bitmap

zend_mm_alloc_pages scans a chunk's free_map for the smallest free run ≥ request (zend_alloc.c, "Best-Fit Search"). A precisely-sized hole is filled by the next allocation that fits it → you place a chosen object at a chosen page.

Two more properties seal it: ZendMM never zeroes on free, and at request end it keeps its chunks (cached_chunks, zend_alloc.c:293) and reuses them for the next request on the same worker. Freed bytes and freed-but-not-nulled pointers both persist. So a pointer that outlives its object — because a longjmp skipped the code that nulls it (§07) — now points at a slot or page the next request deterministically reclaims with attacker bytes. That is the UAF. It appears in two forms:

  • Cross-request (the main chain): PS(id) and the A2 pointer survive into the next request on the pinned worker; the grooming spray reclaims their targets.
  • Intra-request (diagram 7): the callback caches raw zval* interior pointers into the progress array — post_bytes_processed / current_file_bytes_processed (session.c:3306, 3332); php_session_rfc1867_update re-decodes and rebuilds that array (zend_hash_update → zval_ptr_dtor frees the old buckets, :3196–3204), leaving those interior pointers dangling, and the next FILE_DATA event writes through them (Z_LVAL_P(...) = ..., :3334, 3345).

07 — Mechanism

What the OOM trigger actually does

memory_limit is enforced inside the allocator. When serving a request would push heap->real_size past heap->limit (128 MiB), zend_mm_safe_error fires (zend_alloc.c:1049 → 401) → zend_error_noreturn(E_ERROR) → zend_bailout → longjmp(EG(bailout)).

Drive to the limit
The body (chunked, so post_max_size doesn't bound it) allocates aggressively — 860 depth-64 nested arrays, dozens of multi-KB values, a 4000-byte progress value — so real_size climbs to the 128 MiB ceiling. The PoC shapes it so the crossing allocation happens at a chosen moment: for A1, inside the END-cleanup cookie encode (php_url_encode); for A2, earlier (a "cheap" OOM).
What longjmp skips
It unwinds the C stack out of whatever was running — mid-callback, mid-cleanup — straight to the bailout handler, without running the tail of that code. The session code that would reset PS(id)/PS(mod_data) or free-and-null PS(rfc1867_progress) at EVENT_END never runs.
What ZendMM still does
Arena teardown reclaims the pages regardless. So the skipped reset + the reclaimed pages = a live pointer into reusable memory — the strand.
Observed
In gdb each OOM shows as a triple [longjmp]: the first bailout, then cleanup paths that re-allocate while still over the limit and bail again.

A1 strands PS(id) (bin-64) at id_chunk+0x137000 and PS(mod_data) (bin-40) with send_cookie=1. A2 strands hsv = PS(http_session_vars) at main+0x7D720. Each is the input to the B-stage that reclaims it.

08 — Mechanism

Heap grooming, exactly on ZendMM

Grooming = arranging allocations so the reclaim lands where you need it. Here it is, field by field, in ZendMM terms.

B1 — a fake string where PS(id) dangles, libphp pointers beside it

  • G:511:0x137 ×14 — each value is a ~511-page large run that fills a whole 2 MiB chunk with 'A' and writes a forged zend_string header at page 0x137. Fourteen of them pull every cached chunk through this shape, so whichever chunk the stale PS(id) sits in gets the forged header exactly at id_chunk+0x137000. Header fields: refcount 0 (RSHUTDOWN's release decrements to 0xFFFFFFFF, never frees), IS_STRING, len=0xC8000, data '/..' (so valid_key fails — after the cookie is already out).
  • G:400:0x137 — same forged header, but fills only pages 1..400, leaving pages 0x191..0x1ff (111 pages) as a FRUN hole.
  • X:900 — 900 real nested arrays. Their HashTable+Bucket backing Best-Fits into that 111-page hole, and a real HashTable carries pDestructor = zval_ptr_dtor (a libphp pointer). The 0xC8000 window from page 0x137 now spans both the chunk-internal pointers (→ chunk base) and those zval_ptr_dtor pointers (→ libphp).
  • Pure-ZendMM survival trick: releasing the stale basedir string would call zend_string_release on a cached-chunk page and hit zend_mm_panic; the flood values overwrite basedir's chunk so its refcount reads 0x41414141 ≠ 1, making the release a no-op.

B2 — reclaim the A2 strand with a fake callable

  • 384-byte spray → bin-448 (smallest bin ≥ 384), each carrying a fake zend_reference every 32 bytes (rc=1, IS_REFERENCE, ptr=S). Because small reuse is LIFO, these land on the slot the A2 pointer dangles into, so it now reads as a reference to S = main+0xF8398.
  • The ht field places a fake zend_array at S whose pDestructor = zif_system (libphp+0x465370); request shutdown's zend_hash_destroy calls it over a bucket holding the command string → system().
  • --name-len selects the bin for the spray's own keys (3→bin-32, 10→bin-40), used to nudge neighbouring allocations.

12 — The bug

The invariant the chain breaks

Two sites touch PS(rfc1867_progress) and neither per-request hook is one of them — confirmed in 8.4.26:

blind to it

RINIT / RSHUTDOWN

php_rinit_session_globals :108 clears id, mod_data, session_vars… but not rfc1867_progress. php_rshutdown_session_globals :136 dtors vars, closes the handler, releases id… but not rfc1867_progress.

owns it

Callback START / END

Only EVENT_START allocates (ecalloc + set global, :3238) and only EVENT_END frees+nulls (efree(progress); PS(rfc1867_progress)=NULL, :3387–3392). Abort before END and the memory is freed but the global still points at it.

That is …619. …618 is the longjmp that makes aborting-before-END easy and routine. The fix (8.5.12 / 8.4.27 / 8.3.36 / 8.2.35, 21 Oct 2026): …618 stops the request at a safe point instead of longjmp-ing mid-operation; …619 restores the reset so progress state cannot outlive its memory.

13 — Our fork

What we added, and the lab result

Three additions over 9bie's PoC, each forced by a component above.

  • Auto worker discovery (--workers auto). Pinning needs the child count N. A fresh request is served only if a child is free, so the holder count at which a probe first stalls is N; found in O(log N) by exponential ramp then binary search, then hold N−1.
  • Holder keepalive. mod_reqtimeout (body=10,minrate=500) reaps a one-byte holder after ~10s; a background thread drip-feeds ~1.3 KB/s per holder so the pin survives a slower auto-discovery run.
  • Lab harness (lab/labtest.sh). Stock target, N runs with fresh ASLR each, success via the in-container proof file, -w N for an arbitrary worker count, -w auto to drive discovery.

14 — Defense

Detection & patch

Observable from this exploit

  • Set-Cookie: PHPSESSID= far longer than 32 chars (B1 emits ~1.5–2.3 MB)
  • PHPSESSID sent as a POST field, not a Cookie header
  • memory-exhausted fatal with no script/line; the OOM longjmp
  • a burst of long-lived incomplete POSTs (the pin) then a PHP worker spawning sh/id
